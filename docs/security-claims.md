# Security Claims to Verification Map

Maintainers need traceability from each security claim the dashboard makes to the code that
implements it and the check that would catch a regression. Every row names the claim, the
implementation boundary, the automated or manual verification, its known limits, and who reviews it.
[`tests/unit/securityClaims.test.ts`](../tests/unit/securityClaims.test.ts) fails if a path named in
a backticked link below stops existing, so this map cannot silently rot.

For the project-level scope of what is and is not enforced, see
[Enforcement Scope](./enforcement-scope.md). For the README claim inventory, see
[`readme-claims.md`](./readme-claims.md).

## Keeping the map current

When a claim is added, changed or removed, update its row in the same pull request. A new automated
check should add a row (or extend one) and a path that the test above can resolve. A claim that can
only be checked by hand must say so in the Kind column and name the manual step.
